# 有卡环境验证清单

**用途**：拿到一台带 MegaRAID 9460-8i 的机器后，照着这份清单逐项验证。
无卡环境下已经确认的部分见 §0；本清单的重点是 §2 之后**只能在有卡时确认**的项目。

执行环境：fnOS 主机，root 权限。所有命令都是只读的（不创建/删除阵列、不改配置、不刷固件）。

## 1. 不支持：卡在宿主、fnos 是虚机且未直通（S1）

**本方案不支持这种形态，也不需要尝试。**

原理：本应用把 LSA 装进 fnos **自己的** chroot，LSA 通过 fnos 内核的
`/dev/megaraid_sas_ioctl_node` 读卡。如果卡在 PVE 宿主上而 fnos 是普通虚拟机，
fnos 内核里根本没有这张卡，chroot 里的 LSA 同样看不到。

**用户会看到的现象（这是正确行为，不是 bug）**：

```bash
# 1) 门户顶部常驻黄条
#    「本机未检测到 MegaRAID 控制器」
curl -s http://127.0.0.1:2463/status | grep has_card     # → "has_card": false
```
```bash
# 2) LSA 界面能正常打开、能登录
# 3) 但控制器列表为空（0 个控制器）
```
```bash
# 4) 宿主侧能看到设备节点，guest 内看不到
ls -l /dev/megaraid_sas_ioctl_node     # 在 fnOS 内：No such file
```

**给用户的话术**：
> 本应用在 fnOS 本机读取 RAID 卡。你这台 fnOS 是虚拟机，RAID 卡在宿主机上，
> 需要在 PVE 里把整卡直通给这台虚拟机后才能读到（注意：直通前必须确认
> PVE 的系统盘不在这张卡上，否则宿主会起不来）。

## 2. 装前确认（在目标机 fnOS 上）

```bash
# 2.1 CPU 架构与最低指令集（install_init 已自动检查，这里手工复核）
uname -m                                              # 期望 x86_64
grep -qw sse2 /proc/cpuinfo && echo SSE2-OK || echo SSE2-MISSING
# 顺带记录 ISA 等级，排障时会用到
grep -qw avx2 /proc/cpuinfo && echo "有 AVX2" || { grep -qw avx /proc/cpuinfo && echo "有 AVX" || echo "仅 x86-64 基线（无 AVX）"; }
```

期望：`x86_64` + `SSE2-OK`。
若显示"仅 x86-64 基线（无 AVX）"，**正常**——我们用的正是兼容这种 CPU 的 `gcc_8.3.x` 基线。

```bash
# 2.2 驱动是否绑定
grep -l megaraid_sas /sys/class/scsi_host/*/proc_name 2>/dev/null
lsmod | grep megaraid_sas
```
期望：有输出 / 模块已加载。
都没有 → 卡可能没插好、被别的驱动占了、或整卡直通给了别的虚拟机。

```bash
# 2.3 管理设备节点
ls -l /dev/megaraid_sas_ioctl_node
```
期望：存在，形如 `crw------- 1 root root 10, N`。
> **注意**：major/minor 每次驱动重载都可能变，**任何脚本都不要硬编码**。

```bash
# 2.4 端口空闲
ss -lnt | grep -E ':(2463|2464)\b' || echo "2463/2464 空闲"
```

```bash
# 2.5 空间（rootfs 约 270MB + 原包 107MB）
df -h /vol1
grep -E "TRIM_APPDEST_VOL|TRIM_PKGVAR" /var/apps/LSI-Storage-Fnos/cmd/lib/common.sh >/dev/null && echo "目录解析正常"
```

## 4. 等到 READY（**有卡时可能比无卡慢很多**）

```bash
for i in $(seq 1 40); do
  s=$(curl -s --max-time 5 http://127.0.0.1:2463/status)
  echo "$(date +%T) $s" | head -c 200; echo
  case "$s" in *'"READY"'*) break;; esac
  sleep 10
done
```

| 观测 | 含义 |
|---|---|
| 无卡时 12–25 秒就 READY | 已实测 |
| 有卡时更慢（可能 1–5 分钟） | `[待实测]` 卡越多、盘越多越慢；LSA 枚举是逐盘问固件 |
| 超过 10 分钟仍 `WARMING` | 门户会展开自查提示；看 §9 的日志 |

## 5. 控制器枚举 `[有卡才能确认]`

### 5.1 API 层

```bash
B=http://127.0.0.1:2464/lsi/storage/mr/api/1.0
curl -s "$B/servers" | head -40
```

期望：
- `count` ≥ 1
- `values[].properties.health.state` = `OPTIMAL`
- 拿到 `values[].self.uri`（形如 `/lsi/storage/mr/api/1.0/servers/<id>`），后续都用它

```bash
# 记下 server id 供后续使用
SID=$(curl -s "$B/servers" | grep -oE 'servers/[0-9a-f:]{11,}' | head -1 | cut -d/ -f2)
echo "server id = $SID"

curl -s "$B/servers/$SID/controllers" | head -40          # [待实测] 路径
```

期望：能看到控制器条目，其中包含型号（`9460-8i` / `SAS3516` 之类）、固件版本、
以及一个 `self.uri`，其路径里带代次标识（形如 `.../controllers/gen7/0`）。

> **代次不是常量**：不同卡可能是 `gen6`/`gen7`/`gen8`。

## 6. 虚拟盘（VD）`[有卡才能确认]`

逐项核对**界面显示**与**实际配置**是否一致：

| 检查项 | 怎么确认"实际值" | 期望界面显示 |
|---|---|---|
| RAID 级别 | 你在 PVE/BIOS 里建阵列时选的级别 | `RAID1` / `RAID5` / … 与之一致 |
| 容量 | 建阵列时的大小 | 与之一致（十进制 TB/GB） |
| 成员盘数 | 你放进去的盘数 | 例如 RAID5 四盘 = `4` |
| 状态 | 正常应为 OPTIMAL | 绿色「正常」 |
| 名称/编号 | 建阵列时起的名字 | 一致；无名时显示 `VD0` 之类 |

**降级测试（可选，有风险，只在测试盘上做）**：
拔掉一块 RAID5 成员盘 → 刷新界面 → 应显示 `DEGRADED`（橙色），**不是**绿色。
插回后应看到 `REBUILDING`（蓝色）并出现进度。**这一步能验证"状态归一化"是否真的有效**。

## 7. 物理盘（PD）`[有卡才能确认]`

| 检查项 | 怎么确认 | 期望 |
|---|---|---|
| 槽位号 | 看机器背板/硬盘托架上的丝印 | 界面上的槽位与物理槽位**一一对应** |
| 在线状态 | 全部盘都在位 | 每块都显示在线 |
| 介质类型 | 你插的是 HDD 还是 SSD | HDD / SSD 正确 |
| 容量 | 硬盘标称 | 一致 |
| 型号/序列号 | `cat /sys/block/sdX/device/model`（对 VD，不是 PD）| 与盘上标签一致 |
| 温度（若 LSA 提供）| 与机房环境比对 | 合理值；读不到应显示 `—`，**不能显示 0** |
| 错误计数 | 新盘应为 0 | 0；非 0 需关注 |

**空槽位**：界面必须画出空槽（灰色虚线框），否则用户无法区分"盘满了"和"没读到"。

## 12. 只读账号 `[有卡才能确认]`

当前 `LSA.conf` 里写了 `readonly_access_groups = lsiadmin`，
且该键**确实被 `libutility.so` 引用**（说明是真特性，不是死配置）。

**但"只读"是否真的拦住写操作，没有验证过。**

验证方法：
1. 用 `LSI-Storage-Fnos` + 门户展示的口令登录 LSA
2. 找任意一个"会改配置"的入口（创建 VD / 改缓存策略 / 删除 VD 的按钮）
3. 期望：按钮不可见、或点击后被拒绝

| 结果 | 处理 |
|---|---|
| 确实不能写 | ✅ 保留该配置，并在 README 里升级为"已验证" |
| 仍可写 | ❌ **从 `LSA.conf` 删掉这个键**，并在文档里明确「本应用不提供权限隔离，口令即全部权限」——不要留一个假的安全感 |

> 相关事实：LSA 的界面本身就是完整的管理控制台（能建/删阵列、能刷固件）。
> 我们提供的是"只读的使用方式"，不是"只读的权限"。

## 13. 备份与升级 `[部分只能手工验证]`

### 13.1 备份是否排除了 rootfs

`config/resource` 里写了 `backup.exclude`，但**平台是否真的照做没验证过**。

验证：
1. 在 fnOS 控制台做一次系统备份（会碰到用户数据，需用户同意）
2. 备份前记录 `du -sh /vol1/@appdata/LSI-Storage-Fnos /vol1/@appcenter/LSI-Storage-Fnos`
3. 备份后看备份体积是否少了约 372 MB
4. 或查看备份索引里是否出现 `LSI-Storage-Fnos/rootfs`

| 结果 | 处理 |
|---|---|
| 确实排除 | 在 README 里标"已验证" |
| 没排除 | 考虑在 `install_callback` 成功后删除 `target/rootfs.tar.gz`（省 104MB），并接受 rootfs 268MB 会被备份；或改用平台支持的其它排除方式 |

### 13.2 升级

**实测结论：`appcenter-cli` 没有 upgrade 命令，`install-fpk` 对已安装应用是 no-op（同版本、高版本都一样）。**
升级只能通过 App Center 的 UI 升级流程（需要有更新源）。

我们已用直接驱动钩子的方式验证过 `upgrade_init` / `upgrade_callback` 的逻辑：

```
坏载荷 → 解包失败 → 自动回滚 → rc=1 → rootfs 仍可用、指纹完整、无 .prev 残留
好载荷 → 旧 rootfs 保留为 .prev → 解包成功 → 清理回滚点 → rc=0
```

在有卡机器上如果真能触发一次平台升级，要补验：
- `upgrade_init` 是否先于解包执行
- 升级后 `@appdata` 里的端口配置、口令哈希是否保留
- 升级后第一次启动能否正常 READY

## 14. 排障：出问题先看这三处

```bash
# 1) 应用自己的日志
tail -50 /vol1/@appdata/LSI-Storage-Fnos/logs/LSI-Storage-Fnos.log     # 启停、preflight、口令
tail -50 /vol1/@appdata/LSI-Storage-Fnos/logs/lsa.log          # 命名空间挂载、init 脚本调用
tail -50 /vol1/@appdata/LSI-Storage-Fnos/logs/gate.out         # 门户

# 2) LSA 自己的日志（log_level=4，只记 ERROR）
tail -50 /vol1/@appdata/LSI-Storage-Fnos/rootfs/opt/lsi/LSIStorageAuthority/logs/lsa.txt

# 3) 平台侧日志
tail -50 /var/log/apps/LSI-Storage-Fnos.log                    # 钩子的 stdout/stderr
tail -50 /var/log/trim_app_center/error.log            # 平台侧错误码
```

常见现象与指向：

| 现象 | 指向 |
|---|---|
| `Library load failed for plugin : '../plugins/libgateway.so'` | `/opt/lsi/LSA/libs` 不在 `LD_LIBRARY_PATH` 里（补丁 3c 没生效） |
| `nginx: CPU ISA level is lower than required` | 基线选错（必须 `gcc_8.3.x`） |
| `libldap-2.4.so.2 => not found` | 补丁 3d 没生效 |
| `cat: /usr/local/var/log/slpd.log: No such file` | 补丁 3b 没生效（目录没建） |
| 平台报 `code 10237` | 某个钩子返回非 0，看 `/var/log/apps/LSI-Storage-Fnos.log` |
| 门户一直 `STARTING` | 看 `lsa.log` 里 init 脚本是否 `[FAILED]` |
